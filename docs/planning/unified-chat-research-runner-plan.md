# Research Explorer 去繁就简重构计划

- 状态：已确认，待分阶段实施
- 日期：2026-10-06
- 发布版本：待本地试用通过后确定
- 实施方式：本地预览 → 用户试用 → 统一整改 → 用户确认 → 提交与发布
- 需求来源：[CLI 可用性反馈](../reports/usability-feedback.md) UF-008～UF-014、DEC-001～DEC-003

## 1. 目标

Research Explorer 收敛为一个以 Pi 为交互外壳、以 Core 为科研执行内核的统一聊天产品。

用户只需要理解一个顶层对象：**会话**。一个 Pi 会话就是一个科研项目存档，拥有唯一名称、唯一聊天历史和一套可选的结构化科研状态。普通聊天、科研建议、自动科研、人工审批和结果解释都发生在同一条可恢复时间线中。

本轮主要解决：

1. 聊天主题与科研主题重复；
2. Pi session 与 Core Project 双重存档；
3. Candidate/Auto 模式与普通聊天割裂；
4. 候选生成、选择和取消不进入完整历史；
5. Auto 只能执行早期单步动作，无法完成科研流程；
6. 启动选择器缺少明确的新建会话入口。

## 2. 删除的概念

- 删除用户可见的 `manual`、`candidate`、`auto` 模式。
- 删除第二层 Project 选择器。
- 删除全局“最近 Project”绑定。
- 删除回答后的自动候选弹窗。
- 删除“输入自己的方向”“输入其他行动”和显式“取消”选项。
- 删除常驻的内部版本、Workspace、Project ID 和原始状态枚举。

Core 可以暂时保留旧策略字段用于数据兼容，但 CLI 不再使用它们决定聊天交互。

## 3. 唯一存档模型

### 3.1 会话即项目

- Pi session ID 是面向产品的唯一存档身份。
- Pi session name 是唯一用户可见标题。
- Core Project ID 变为内部实现标识，不在普通界面展示。
- Core 保存 `piSessionId ↔ projectId` 映射。
- 一个会话最多对应一个 Core Project；一个 Core Project不再被多个独立聊天隐式共享。

### 3.2 延迟创建科研状态

新会话首先只是普通聊天，不立即创建 Core Project。以下操作首次发生时，Core 才建立结构化科研状态：

- `/run` 启动自动科研；
- 调用证据、假设、实验设计、统计或写作能力；
- 用户明确要求保存为结构化科研记录。

创建时使用当前 Pi session name 作为项目标题，并把创建事件作为可见会话消息记录。

### 3.3 唯一历史

- 用户消息、模型回答、科研建议、任务启动、计划变更、门禁审批、失败和最终结果都写入 Pi session。
- Core 只保存可审计的结构化对象、事件、Job 和 Artifact。
- 每个 Core 对象记录来源 session ID 和 message/entry ID。
- 不再维护第二套 Core conversation 历史。
- Compaction、resume、tree、fork 和 clone 继续由 Pi 原生机制负责。

### 3.4 分叉

Pi 会话发生 fork/clone 时：

1. 新 Pi session 获得新身份；
2. Core 从当前科研快照创建派生 Project；
3. 新旧会话分别绑定自己的 Project；
4. 分叉事件和来源进入两边可见历史；
5. 已冻结协议与确认数据权限继续遵守 Core 规则。

## 4. 启动体验

无参数运行 `rexplore` 时显示一层统一存档页：

1. **新建会话**；
2. 最近会话，显示名称、更新时间和简短科研进度；
3. 搜索全部会话；
4. 退出。

选择历史会话后，Pi 恢复聊天，Core 根据 session ID 恢复科研状态。选择新建会话后直接进入空白聊天，不再出现 Project 选择器。

实现优先复用 Pi 的公开 SessionManager 和会话元数据。若 Pi 当前选择器无法加入“新建会话”，在 launcher 中增加最小启动适配层；不复制 Pi 的完整 TUI、session 存储或导航逻辑。

保留原生快捷入口：

- `rexplore -c`：继续最近会话；
- `rexplore -r`：进入统一存档页；
- `/new`：当前界面中新建会话；
- `/resume`：切换会话。

## 5. 统一聊天命令

### 5.1 保留的主要命令

| 命令 | 作用 |
| --- | --- |
| `/next [要求]` | 在正常聊天中请求若干下一步研究建议 |
| `/run [目标]` | 启动或继续自动科研任务 |
| `/run-status` | 查看计划、当前步骤、预算、阻塞和产物 |
| `/pause` | 在安全边界暂停自动科研 |
| `/continue` | 从持久化检查点继续 |
| `/stop` | 终止自动任务并保留已有结果 |
| `/status` | 显示当前会话的简短科研状态 |
| `/report [path]` | 生成事实约束报告 |
| `/doctor` | 显示诊断信息和内部 ID |

插件、SSH、Bundle 和高级能力命令继续存在，但不进入默认的新手命令列表。

### 5.2 `/next`

`/next` 不发起独立候选模式，也不显示第二套选择框。它转换成一条正式用户消息，由正常 Pi agent turn 回答，例如：

> 根据当前聊天和科研状态，给出三个差异明确的下一步方向。每项说明目标、下一步、理由、成本和风险。不要执行，等待我选择或自由输入。

模型回答是普通 assistant message，完整进入历史、usage、分叉和 compaction。用户可以回复编号、组合方案或任意文字，不需要专门的“其他”选项。

## 6. 自动科研运行器

### 6.1 `/run` 不是聊天模式

`/run` 创建一个持久化 `ResearchRun`，由 Core 调度，聊天只负责观察、指导和审批。退出 CLI 不取消运行；重新进入同一会话可以恢复进度。

### 6.2 固定阶段骨架

自动科研按以下骨架推进：

1. 问题界定；
2. 文献与证据；
3. 竞争假设与可判别预测；
4. 协议与实验设计；
5. 基线复现；
6. 有界探索；
7. 候选冻结；
8. 确认实验；
9. 统计分析与结果解释；
10. 独立审查与回应；
11. 事实约束报告与最终决策。

不是每个研究都必须运行全部阶段。Planner 根据研究类型声明适用阶段，但不得跳过适用的强制门禁。

### 6.3 阶段内动态计划

每个阶段开始时，Planner 生成版本化 `StepPlan`：

- 目标和完成条件；
- 输入对象与证据来源；
- 使用的公共科研能力或 Job；
- 预算与预计耗时；
- 风险、失败分类和停止条件；
- 对应的 session entry ID。

Executor 一次只领取一个可执行步骤。步骤完成后，Verifier 根据 Core 事实检查结果，再决定完成阶段、修订计划或进入阻塞。

### 6.4 不允许“没有下一步计划”直接结束

Planner 找不到动作时必须产生以下结果之一：

1. `ready_step`：明确的下一步；
2. `awaiting_approval`：说明需要哪个人工决定；
3. `blocked`：列出缺失环境、权限、数据、依赖或预算，并给出恢复办法；
4. `completed`：列出完成证据与产物。

空计划、泛化建议或无原因停止均视为运行器错误。

### 6.5 人工门禁

自动运行持续推进，只有以下情况暂停：

- 研究范围批准；
- 协议冻结；
- 确认数据或最终测试解封；
- 最终结论与报告确认；
- 权限扩大或高风险外部副作用；
- 成本墙、时间墙或资源墙触发；
- 无法自动恢复的真实阻塞。

门禁作为结构化消息进入当前 Pi session。用户批准、拒绝或修改后，决定同样进入历史和 Core 审计。

### 6.6 任务控制

`ResearchRun` 至少包含：

- `queued | running | awaiting_approval | paused | blocked | completed | failed | cancelled`；
- 当前阶段、步骤和计划版本；
- 累计模型调用、已知费用、运行时间、磁盘和 GPU 使用；
- 最近检查点和可恢复信息；
- Job、Artifact、证据和报告引用；
- 阻塞原因和恢复动作。

暂停在当前原子步骤结束或安全中断点生效。继续运行必须验证依赖、权限、预算和冻结对象没有漂移。

## 7. 界面原则

- 普通聊天不显示常驻科研 widget。
- 自动任务运行时只显示一行简短进度，例如“证据检索 3/8 · $0.12 · 12m”。
- 详细计划、内部 ID、Workspace、Worker 和调试信息放在 `/run-status` 或 `/doctor`。
- 所有阶段使用用户可理解的中文名称。
- 每个后台动作都必须能从聊天历史跳转到对应日志或 Artifact。

## 8. 兼容与迁移

1. 读取旧 Pi session 中的 `research-explorer.context`，建立 session ID 到旧 Project 的一次性映射。
2. 忽略旧全局 `~/.research-explorer/state.json`，但首次升级时备份并记录迁移结果。
3. 将旧 `candidate`/`auto` policy 迁移为统一聊天，不恢复自动弹窗或单步 Auto。
4. `/mode` 暂时保留，只显示迁移说明；后续版本删除。
5. 旧 `/research-*` 命令继续兼容一个发布周期。
6. 已存在的 Job、Artifact、Bundle 和审计事件保持可读。

## 9. 实施阶段

### P0：冻结语义与回归基线

- 固定本计划、数据迁移规则和验收样例。
- 保存当前 v0.2.0 本地回滚包。
- 为会话、Core Project、候选历史和旧 Auto 建立迁移 fixture。

### P1：会话即项目

- 新增 session/project 映射公共契约。
- 移除全局最近 Project 和第二层 Project picker。
- 实现科研状态延迟创建。
- 把 Pi session name 作为唯一用户标题。

### P2：统一启动与历史

- 启动页增加明确“新建会话”。
- 历史列表附带可选科研进度摘要。
- 验证 resume、new、tree、fork、clone 和 compaction。

### P3：删除模式并重做 `/next`

- 删除 Candidate/Auto 路由和弹窗。
- `/next` 进入普通 Pi turn。
- 验证建议、选择和自由输入全部出现在同一历史中。

### P4：ResearchRun 与 Planner

- 新增 ResearchRun、StagePlan、StepPlan、checkpoint 和 blocker 契约。
- 实现固定阶段骨架、阶段内动态规划、Verifier 和空计划失败门。
- 接入现有科研能力、Job、Artifact、预算和人工门禁。

### P5：CLI 自动任务控制

- 实现 `/run`、`/run-status`、`/pause`、`/continue` 和 `/stop`。
- 添加简洁进度展示和聊天内审批。
- 验证 CLI 退出后任务继续、重启后恢复和安全暂停。

### P6：本地试用验收

- 从本地源码构建 Core/CLI 包并安装到当前用户环境。
- 在 `/data0/linsihan/test` 完成真实 API 试用。
- 用户集中反馈并统一整改。
- 不提交正式版本、不推送发布提交、不发布 npm，直到用户明确确认。

## 10. 验收门禁

### 存档与历史

- 新建会话入口清楚可见。
- 一个会话只对应一个科研状态。
- 普通聊天不会创建空 Core Project。
- `/next` 的请求、回答和用户选择全部存在于 Pi history。
- resume、fork、clone 和 compaction 后没有轮次缺失。

### 自动科研

- `/run` 可以从空聊天形成问题并推进到第一个人工门禁。
- 批准后能继续跨越至少三个不同科研阶段。
- CLI 退出和 Core 重启后可以恢复。
- 暂停、继续、停止均保持状态一致。
- 没有可执行步骤时必须返回审批、阻塞或完成，不得返回空计划。
- 预算、时间、权限和确认数据门禁均 fail closed。

### 界面与兼容

- 默认界面无 C5、长 ID、Workspace 或英文内部状态。
- 无 Manual/Candidate/Auto 模式选择。
- Linux、macOS ARM 和 macOS Intel 通过。
- 旧会话与旧 Project 可以迁移、读取和导出。
- API Key、Core token、确认 token 和 SSH 私钥不进入 session、日志、Bundle 或发布包。

## 11. 发布规则

本计划实施期间只交付本地预览。每轮完成后：

1. 自动测试；
2. 本地打包；
3. 安装到当前用户环境；
4. 用户在 `test` 目录试用；
5. 登记反馈并统一整改。

只有用户明确验收通过后，才确定正式版本号、提交发布证据、推送 Git 和发布 npm。
