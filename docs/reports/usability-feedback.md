# Research Explorer CLI 可用性反馈

本文件记录实际试用过程中发现的问题。UF-001 至 UF-007 已在 v0.2.0 统一整改；各项保留原始观察与设计依据，最终实现由自动化门禁和实际终端验收共同确认。

## UF-001：科研快捷命令前缀过长

- 状态：已整改（v0.2.0）
- 来源：实际终端试用
- 现状：所有科研命令都使用 `/research-*` 形式，例如 `/research-mode`、`/research-next`、`/research-status`。
- 问题：高频操作需要反复输入 `research` 前缀，命令冗长，降低交互效率和使用便利性。
- 期望：缩短高频命令，减少重复前缀，同时保持命令易理解、可发现，并避免与 Pi 原生命令冲突。
- 待统一决策：确定短命令命名、旧命令兼容周期、帮助与自动补全展示方式。

## UF-002：候选模式没有在入口立即提供选项

- 状态：已整改（v0.2.0）
- 来源：实际终端试用
- 现状：切换到 `candidate` 模式后仍先显示普通聊天输入框；用户提交一轮聊天内容后，系统才显示候选项。
- 问题：当前流程让候选模式表现为“聊天后的附加选择”，没有形成以候选节点为入口的交互方式。
- 期望：进入或切换到候选模式后立即弹出若干下一步选项，其中固定包含“自由聊天/自由输入”；用户无需先提交一轮聊天才能看到候选项。
- 初步判断：这属于当前交互触发时机与产品预期不一致，需要统一整改候选生成、初始状态和界面触发流程。
- 待统一决策：首次候选的生成来源、无活动项目时显示的选项、刷新候选方式，以及取消后返回何种界面。

## UF-003：候选内容只是状态机动作，不是详细的研究方向

- 状态：已整改（v0.2.0）
- 来源：实际终端试用与代码核查
- 用户预期：Agent 完成一轮回答后，继续生成若干有实质内容的可能方向，包括候选目标、下一步行动、理由和差异，供用户选择；其中保留自由聊天入口。
- 当前实现：候选由 Core 的确定性 `legalActions` 产生，只覆盖 `question.propose`、`question.select` 和 `scope.approve` 三类状态机动作，并非由模型根据刚完成的回答生成研究方向。
- 当前展示：选择框只渲染候选的 `title`，没有展示 `description`、`rationale`、预期信息增益、成本、风险和停止条件；描述目前仅在人工批准确认框中出现。
- 当前边界：当状态机没有上述合法动作时，系统不会生成新的研究方向候选，用户看到的可能只剩自由聊天、其他行动和取消。
- 结论：现有候选模式实现了“合法动作选择”，尚未实现“回答后生成详细研究分支、目标和下一步”的产品设想。
- 待统一决策：设计模型生成候选与 Core 合法性校验的组合流程、候选卡片信息结构、生成数量、排序与刷新机制，以及回答完成后的自动触发时机。

## UF-004：重新启动时没有统一的聊天与项目存档选择

- 状态：已整改（v0.2.0）
- 来源：实际终端试用与代码核查
- 用户预期：像 Codex 一样，启动后可以继续最近会话或从历史聊天/科研项目中选择一个存档，也可以明确创建新聊天或新项目。
- 当前聊天行为：`rexplore` 只是把参数透传给 Pi；无参数启动时使用 Pi 的新会话行为，因此不会自动显示历史选择器。Pi 原生的 `rexplore -c` 可以继续当前目录最近会话，`rexplore -r` 可以打开会话选择器，但产品入口没有呈现这些选项。
- 当前项目行为：CLI 将最近一个 Project 的非敏感绑定写入状态文件，启动后尝试自动恢复它；这只能恢复最近项目，不能列出并选择全部科研项目。
- 当前阻塞：Core 尚未提供 `workspace.projects` 公共查询，CLI 的 `/research-open` 必须由用户手工输入 Project ID，因此无法实现正式的项目选择器。
- 结论：当前存在 Pi 聊天会话与 Core 科研 Project 两套存档语义。普通启动可能呈现空白新聊天，同时后台绑定最近 Project，没有形成用户可理解的统一存档入口。
- 待统一决策：启动首页的“继续最近聊天、选择聊天、选择项目、新建聊天、新建项目”信息架构，聊天与 Project 的绑定关系，以及 Core `workspace.projects` 接口和排序/搜索规则。

## UF-005：全局最近项目污染所有新聊天

- 状态：已整改（v0.2.0）
- 来源：实际终端试用、运行状态与代码核查
- 复现现象：首次创建“世界模型入门”后，随后直接启动的多个新聊天都显示“世界模型入门”。
- 根因：CLI 将最近 Project 写入全局 `~/.research-explorer/state.json`。新 Pi 会话没有自身的 Project 绑定时，`session_start` 会无条件回退读取该全局文件，因此不同聊天和不同工作目录都会自动绑定同一个最近 Project。
- 实际状态：这些聊天没有加载同一份 Pi 聊天历史；它们只是共享了同一个 Core Project 标题、ID、模式和 conversation session 绑定。
- 风险：用户无法区分“继续原项目”“新聊天但沿用项目”和“完全新建研究”；还可能把新对话内容错误写入此前项目。
- 期望：新聊天默认不应静默继承全局最近 Project。项目绑定应至少按 Pi session 隔离，并由用户在启动入口明确选择继续最近项目、选择其他项目或不绑定项目。
- 待统一决策：是否取消全局 fallback、是否按工作目录保存最近绑定、聊天与 Project 的一对一/多对一关系，以及旧 `state.json` 的兼容迁移策略。

## UF-006：常驻界面暴露内部版本、长 ID 和原始状态值

- 状态：已整改（v0.2.0）
- 来源：实际终端试用与代码核查
- 当前展示：顶部状态栏持续显示 `C5 · <mode> · <status> · <short-id>`；下方 widget 又显示 `Research Explorer C5`、项目标题、原始状态、Workspace ID 和完整 Project ID。
- 问题：`C5` 是内部开发阶段编号；`program-...` 和 `workspace:default` 是机器标识；`scoped` 是未经解释的领域状态。它们长期占用界面并重复展示，对普通用户没有直接操作价值。
- 期望：默认界面只保留项目标题、用户可理解的中文阶段和必要的运行状态；版本、Workspace、Project ID 等诊断信息移入 doctor、详情页或可展开区域。
- 待统一决策：状态栏与 widget 的最小信息集、科研阶段的用户文案和进度表达、诊断信息入口，以及高级用户是否可以开启详细模式。

## UF-007：自由聊天模式不应常驻显示科研状态

- 状态：已整改（v0.2.0）
- 来源：实际终端试用
- 当前行为：`manual` 自由聊天模式仍常驻显示 Research Explorer、项目标题、科研阶段、模式、Workspace 和 Project ID 等状态信息。
- 问题：自由聊天模式本应保持接近 Pi/Codex 的普通聊天体验；持续展示科研流程状态会造成界面干扰，也会让用户误以为每次自由聊天都会推进或写入当前科研项目。
- 期望：自由聊天模式默认隐藏科研状态栏和科研 widget。只有用户主动打开科研项目、进入候选/自动模式、调用科研命令，或显式查看状态时才展示相关信息。
- 待统一决策：自由聊天与科研项目是否允许保持后台绑定、进入/退出科研工作区的显式动作、临时状态提示持续时间，以及如何提示一次操作是否会写入科研项目。


## v0.2.0 整改结果

- 提供 `/doctor`、`/project`、`/status`、`/mode`、`/next`、`/actions`、`/report` 等短命令，并保留旧命令兼容。
- 候选模式进入时立即生成方向；正常回答结束后再生成三个包含目标、下一步和理由的候选，始终保留自由聊天与自定义方向。
- `rexplore` 交互启动默认进入 Pi 会话选择器；新聊天随后进入 Core 项目选择器。
- Core 新增公共 `workspace.projects` 查询，项目选择不再要求复制长 ID。
- Project 绑定只写入当前 Pi session；全局 `state.json` 不再作为新聊天 fallback。
- 默认界面移除 C5、Workspace 和 Project ID；阶段转换为中文。自由聊天模式隐藏科研状态栏与 widget。
