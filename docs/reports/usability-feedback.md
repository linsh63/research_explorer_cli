# Research Explorer CLI 可用性反馈

本文件记录实际试用过程中发现的问题。UF-001 至 UF-007 已在 v0.2.0 统一整改；各项保留原始观察与设计依据，最终实现由自动化门禁和实际终端验收共同确认。

UF-008～UF-014 和后续架构决策已收敛为[统一聊天与自动科研运行器计划](../planning/unified-chat-research-runner-plan.md)。

## UF-001：科研快捷命令前缀过长

- 状态：已整改（v0.2.0）
- 来源：实际终端试用
- 现状：所有科研命令都使用 `/research-*` 形式，例如 `/research-mode`、`/research-next`、`/research-status`。
- 问题：高频操作需要反复输入 `research` 前缀，命令冗长，降低交互效率和使用便利性。
- 期望：缩短高频命令，减少重复前缀，同时保持命令易理解、可发现，并避免与 Pi 原生命令冲突。
- 待统一决策：确定短命令命名、旧命令兼容周期、帮助与自动补全展示方式。

## UF-002：候选模式没有在入口立即提供选项

- 状态：已整改（v0.2.0）
- 来源：实际终端试用
- 现状：切换到 `candidate` 模式后仍先显示普通聊天输入框；用户提交一轮聊天内容后，系统才显示候选项。
- 问题：当前流程让候选模式表现为“聊天后的附加选择”，没有形成以候选节点为入口的交互方式。
- 期望：进入或切换到候选模式后立即弹出若干下一步选项，其中固定包含“自由聊天/自由输入”；用户无需先提交一轮聊天才能看到候选项。
- 初步判断：这属于当前交互触发时机与产品预期不一致，需要统一整改候选生成、初始状态和界面触发流程。
- 待统一决策：首次候选的生成来源、无活动项目时显示的选项、刷新候选方式，以及取消后返回何种界面。

## UF-003：候选内容只是状态机动作，不是详细的研究方向

- 状态：已整改（v0.2.0）
- 来源：实际终端试用与代码核查
- 用户预期：Agent 完成一轮回答后，继续生成若干有实质内容的可能方向，包括候选目标、下一步行动、理由和差异，供用户选择；其中保留自由聊天入口。
- 当前实现：候选由 Core 的确定性 `legalActions` 产生，只覆盖 `question.propose`、`question.select` 和 `scope.approve` 三类状态机动作，并非由模型根据刚完成的回答生成研究方向。
- 当前展示：选择框只渲染候选的 `title`，没有展示 `description`、`rationale`、预期信息增益、成本、风险和停止条件；描述目前仅在人工批准确认框中出现。
- 当前边界：当状态机没有上述合法动作时，系统不会生成新的研究方向候选，用户看到的可能只剩自由聊天、其他行动和取消。
- 结论：现有候选模式实现了“合法动作选择”，尚未实现“回答后生成详细研究分支、目标和下一步”的产品设想。
- 待统一决策：设计模型生成候选与 Core 合法性校验的组合流程、候选卡片信息结构、生成数量、排序与刷新机制，以及回答完成后的自动触发时机。

## UF-004：重新启动时没有统一的聊天与项目存档选择

- 状态：已整改（v0.2.0）
- 来源：实际终端试用与代码核查
- 用户预期：像 Codex 一样，启动后可以继续最近会话或从历史聊天/科研项目中选择一个存档，也可以明确创建新聊天或新项目。
- 当前聊天行为：`rexplore` 只是把参数透传给 Pi；无参数启动时使用 Pi 的新会话行为，因此不会自动显示历史选择器。Pi 原生的 `rexplore -c` 可以继续当前目录最近会话，`rexplore -r` 可以打开会话选择器，但产品入口没有呈现这些选项。
- 当前项目行为：CLI 将最近一个 Project 的非敏感绑定写入状态文件，启动后尝试自动恢复它；这只能恢复最近项目，不能列出并选择全部科研项目。
- 当前阻塞：Core 尚未提供 `workspace.projects` 公共查询，CLI 的 `/research-open` 必须由用户手工输入 Project ID，因此无法实现正式的项目选择器。
- 结论：当前存在 Pi 聊天会话与 Core 科研 Project 两套存档语义。普通启动可能呈现空白新聊天，同时后台绑定最近 Project，没有形成用户可理解的统一存档入口。
- 待统一决策：启动首页的“继续最近聊天、选择聊天、选择项目、新建聊天、新建项目”信息架构，聊天与 Project 的绑定关系，以及 Core `workspace.projects` 接口和排序/搜索规则。

## UF-005：全局最近项目污染所有新聊天

- 状态：已整改（v0.2.0）
- 来源：实际终端试用、运行状态与代码核查
- 复现现象：首次创建“世界模型入门”后，随后直接启动的多个新聊天都显示“世界模型入门”。
- 根因：CLI 将最近 Project 写入全局 `~/.research-explorer/state.json`。新 Pi 会话没有自身的 Project 绑定时，`session_start` 会无条件回退读取该全局文件，因此不同聊天和不同工作目录都会自动绑定同一个最近 Project。
- 实际状态：这些聊天没有加载同一份 Pi 聊天历史；它们只是共享了同一个 Core Project 标题、ID、模式和 conversation session 绑定。
- 风险：用户无法区分“继续原项目”“新聊天但沿用项目”和“完全新建研究”；还可能把新对话内容错误写入此前项目。
- 期望：新聊天默认不应静默继承全局最近 Project。项目绑定应至少按 Pi session 隔离，并由用户在启动入口明确选择继续最近项目、选择其他项目或不绑定项目。
- 待统一决策：是否取消全局 fallback、是否按工作目录保存最近绑定、聊天与 Project 的一对一/多对一关系，以及旧 `state.json` 的兼容迁移策略。

## UF-006：常驻界面暴露内部版本、长 ID 和原始状态值

- 状态：已整改（v0.2.0）
- 来源：实际终端试用与代码核查
- 当前展示：顶部状态栏持续显示 `C5 · <mode> · <status> · <short-id>`；下方 widget 又显示 `Research Explorer C5`、项目标题、原始状态、Workspace ID 和完整 Project ID。
- 问题：`C5` 是内部开发阶段编号；`program-...` 和 `workspace:default` 是机器标识；`scoped` 是未经解释的领域状态。它们长期占用界面并重复展示，对普通用户没有直接操作价值。
- 期望：默认界面只保留项目标题、用户可理解的中文阶段和必要的运行状态；版本、Workspace、Project ID 等诊断信息移入 doctor、详情页或可展开区域。
- 待统一决策：状态栏与 widget 的最小信息集、科研阶段的用户文案和进度表达、诊断信息入口，以及高级用户是否可以开启详细模式。

## UF-007：自由聊天模式不应常驻显示科研状态

- 状态：已整改（v0.2.0）
- 来源：实际终端试用
- 当前行为：`manual` 自由聊天模式仍常驻显示 Research Explorer、项目标题、科研阶段、模式、Workspace 和 Project ID 等状态信息。
- 问题：自由聊天模式本应保持接近 Pi/Codex 的普通聊天体验；持续展示科研流程状态会造成界面干扰，也会让用户误以为每次自由聊天都会推进或写入当前科研项目。
- 期望：自由聊天模式默认隐藏科研状态栏和科研 widget。只有用户主动打开科研项目、进入候选/自动模式、调用科研命令，或显式查看状态时才展示相关信息。
- 待统一决策：自由聊天与科研项目是否允许保持后台绑定、进入/退出科研工作区的显式动作、临时状态提示持续时间，以及如何提示一次操作是否会写入科研项目。


## v0.2.0 整改结果

- 提供 `/doctor`、`/project`、`/status`、`/mode`、`/next`、`/actions`、`/report` 等短命令，并保留旧命令兼容。
- 候选模式进入时立即生成方向；正常回答结束后再生成三个包含目标、下一步和理由的候选，始终保留自由聊天与自定义方向。
- `rexplore` 交互启动默认进入 Pi 会话选择器；新聊天随后进入 Core 项目选择器。
- Core 新增公共 `workspace.projects` 查询，项目选择不再要求复制长 ID。
- Project 绑定只写入当前 Pi session；全局 `state.json` 不再作为新聊天 fallback。
- 默认界面移除 C5、Workspace 和 Project ID；阶段转换为中文。自由聊天模式隐藏科研状态栏与 widget。

## UF-008：候选中的“输入自己的方向”与自由聊天重复

- 状态：本地预览已调整，待用户试用
- 来源：v0.2.0 实际终端试用
- 当前行为：候选列表同时提供“自由聊天（返回输入框）”和“输入自己的方向”。
- 问题：两者都允许用户脱离预设候选并表达自己的意图，语义和功能高度重叠，增加选择成本。
- 建议：删除“输入自己的方向”，只保留自由聊天入口。用户返回输入框后可以完整表达任何自定义方向。
- 待决策：自由聊天是否直接关闭本轮候选，以及用户输入后是否在回答结束时重新生成候选。

## UF-009：候选交互与聊天历史割裂，出现轮次缺失

- 状态：本地预览已调整，待用户试用
- 来源：v0.2.0 实际终端试用
- 现象：自由聊天的消息历史和候选生成/选择历史不能作为同一条连续时间线显示。用户向上查看时看不到完整的实际交互轮次，存在候选生成、取消或选择过程缺失。
- 根因方向：普通回答属于 Pi session transcript；候选由扩展在 `turn_end` 后发起独立模型调用并使用临时选择框展示。候选请求、模型结果和用户选择没有完整写入同一套可恢复的聊天记录。
- 影响：会话恢复、向上回看、分叉、压缩和上下文理解看到的历史可能与用户实际经历不一致；模型也未必知道用户看过或拒绝过哪些候选。
- 用户预期：候选模式应是普通聊天的一种显示或导航方式，所有回答、候选、选择、取消和后续输入都属于同一条聊天时间线，不应形成第二套隐形历史。
- 待决策：候选是否作为结构化消息写入 Pi session、选择是否成为正式用户消息、取消是否记录，以及候选生成调用和使用量如何进入会话与科研预算。

## DEC-001：重新评估是否保留候选模式

- 状态：本地预览暂时停用独立候选模式，待用户试用后决策
- 背景：候选模式虽已实现详细方向，但仍与 Pi 原生聊天、历史、恢复、分叉和 compaction 机制存在明显割裂。修补独立候选 UI 可能继续增加双重交互语义和维护成本。
- 方案 A：保留候选模式，将候选完整整合为 Pi session 中的结构化消息和正常聊天轮次。
- 方案 B：取消独立候选模式，在普通聊天中提供可选的“回答后建议下一步”能力；候选只是普通回答的一部分。
- 方案 C：保留 `/next` 作为用户主动调用的单次建议功能，删除自动弹出的候选模式。
- 后续讨论重点：聊天历史一致性、操作复杂度、模型调用成本、科研流程约束、Pi 原生能力复用程度，以及候选功能是否带来足够的实际价值。

## UF-010：Auto 模式没有形成可感知的自动推进

- 状态：本地预览暂时停用 Auto，待用户试用后决策
- 来源：v0.2.0 实际终端试用
- 用户预期：进入 Auto 模式后，Agent 应在预算和人工门禁范围内连续完成可以自动执行的研究步骤，并清楚展示正在做什么、为何停止以及下一步需要什么。
- 当前行为：Auto 只允许 Core 在单轮内执行至多一个零成本、无额外权限的早期状态动作。它不会连续运行完整科研链路，也不会主动规划和调度后续工作，因此实际体验接近“仍需用户逐步推动”。
- 问题：模式名称暗示持续自治，但当前能力只是非常有限的单步策略，用户难以感受到它在自动运行。
- 待决策：Auto 应升级为可暂停、可观察、有预算墙和人工门禁的连续执行循环，还是删除该模式并用显式任务/队列替代。

## UF-011：Auto 模式存在“输入其他行动”和“取消”冗余选项

- 状态：本地预览已移除相关按钮，待用户试用
- 来源：v0.2.0 实际终端试用
- 当前行为：Auto 流程仍可能显示 Core 合法动作选择器，其中包含“输入其他行动”和“取消”。
- 问题：“输入其他行动”与返回普通聊天重复；“取消”在自动模式中语义不清，用户无法判断是取消当前选择、本轮自动执行、当前任务还是整个 Auto 模式。
- 建议：若保留 Auto 模式，正常自动步骤不应显示手工候选菜单；需要用户介入时只显示具体门禁选择，并使用含义明确的“暂停自动运行”或“退出自动模式”。

## DEC-002：重新评估是否保留 Auto 模式

- 状态：本地预览采用方案 A（暂时删除用户可见 Auto），待用户试用后决定是否永久采用
- 方案 A：删除 Auto 模式，只保留自由聊天和显式科研任务。
- 方案 B：将 Auto 重做为持续执行的科研任务运行器，提供计划、进度、暂停、继续、成本墙、时间墙和人工门禁。
- 方案 C：保留当前单步能力，但改名为“辅助推进”或“单步自动”，避免形成持续自治的错误预期。
- 与候选模式的关系：如果候选模式也被删除，产品可以收敛为“统一聊天 + 显式任务运行 + 必要人工门禁”，减少三套交互语义之间的冲突。

## DEC-003：采用本地试用后再发布的迭代流程

- 状态：已确认
- 规则：后续每轮修改完成后，不立即发布 npm 新版本，也不把“代码完成”直接视为产品验收通过。
- 本地预览：在 Core 与 CLI 仓库完成实现和自动化测试后，从本地源码构建包并安装到当前用户环境；用户在 `/data0/linsihan/test` 目录直接运行 `rexplore` 试用。
- 文件边界：API、模型和凭据配置继续保存在用户配置目录；不向 Core 或 CLI 项目仓库写入测试凭据。`test` 目录只作为实际使用入口，不复制项目源码。
- 反馈循环：用户继续登记实际问题；同一轮问题讨论收敛后再统一整改并重新同步本地预览。
- 发布门禁：只有用户明确确认本地试用结果可接受后，才更新正式版本号、生成发布证据、Git 提交/推送并发布 npm。
- 例外：用户明确要求立即提交、推送或发布时，按该次指令执行。

## UF-012：科研主题与聊天主题形成两套冲突语义

- 状态：高优先级，待本轮设计讨论
- 来源：统一聊天本地预览试用
- 现象：Pi 会话有自己的聊天名称和上下文，Core Project 又有独立科研标题、状态与存档。创建、恢复或切换时，用户需要同时理解“我在哪个聊天里”和“我在哪个科研项目里”。
- 问题：聊天和科研项目都被当作顶层容器，名称、历史、恢复、分叉和当前状态可能不一致，形成双重主题与双重存档。产品为了连接两者增加了绑定文件、恢复逻辑、选择器和状态提示，复杂度持续外溢到所有模式。
- 用户判断：现有设计可能从根本上过度复杂，需要重新确定唯一的顶层对象，而不是继续修补聊天与 Project 的绑定关系。
- 待决策：Project 是否直接等同于一个 Pi 会话、一个 Project 是否允许多个会话、自由聊天是否属于 Project、会话分叉如何映射科研分支，以及哪个系统拥有名称和历史的唯一事实来源。

## UF-013：启动选择器没有明确的新建会话入口

- 状态：本地预览已修复，待用户试用
- 来源：本地预览实际终端试用
- 当前行为：无参数运行 `rexplore` 会启动 Pi 的 `--resume` 会话选择器。该选择器主要展示已有会话；虽然取消选择后可能落回空会话，但界面没有清楚的“新建会话”选项。
- 问题：用户只能明显看到已有会话，无法理解如何开始新聊天，实际体验等同于不能创建新会话。
- 期望：启动页第一项明确提供“新建会话”，其后显示最近会话；新建后直接进入统一聊天，不再追加第二层 Project 选择器。
- 关联决策：在“一个会话就是一个项目”的新模型下，创建新会话同时创建唯一用户存档；Core 科研状态在首次使用科研能力时延迟建立。

## UF-014：需要独立的自动科研任务，而不是 Auto 聊天模式

- 状态：关键重构目标，待最终边界确认
- 来源：本地预览与此前 Auto 模式试用
- 已确认：删除 Manual/Candidate/Auto 模式系统，保留统一聊天；保留 `/next` 作为用户主动请求下一步建议的命令。
- 新需求：提供一个独立命令直接启动自动科研。启动后，系统应按照预定科研工作流持续推进，而不是要求用户每轮推动。
- 当前缺陷：旧 Auto 依赖 `legalActions`，该接口只覆盖提出问题、选择问题和批准范围等少量早期状态动作。离开这些动作后会报告“没有下一步计划”，无法覆盖证据、假设、协议、实验、分析、审查和报告链路。
- 架构方向：自动科研应作为持久化任务运行器，拥有显式计划、当前步骤、预算、日志、暂停/继续、失败分类和人工门禁；聊天只是观察、指导和审批任务的界面。
- 候选命令：使用简短 `/run` 启动或继续自动科研，配套 `/run-status`、`/pause` 和 `/continue`；最终命名在规划收束时确定。

## UF-015：Core 的早期合法动作被误当成完整科研计划

- 状态：本地预览已整改，待用户试用
- 来源：统一聊天与 `/run` 实际试用
- 现象：自动科研反复显示“当前阶段没有可自动推进的行动”，无法进入文献、假设、协议、实验、分析和报告阶段。
- 根因：Core `conversation/legalActions` 只负责问题提出、问题选择和范围批准，但 CLI 与模型曾把它当成完整流程的下一步规划器。Project 离开早期状态后没有这三类动作，返回空动作是契约内的正常结果。
- 整改：ResearchRun 成为完整科研流程的唯一阶段计划来源；`research_converse` 明确限制在 draft 阶段；已有 Project 按 Core 生命周期恢复到 evidence、protocol、baseline 或 analysis 等适当阶段；新任务先自动完成安全的问题提出与选择；`/continue` 在同一流程内办理范围批准，不再要求用户转去 `/actions`。
- 防回归：系统提示明确规定 Core 的空动作不构成 ResearchRun 阻塞；新增已有 scoped Project 直接进入证据阶段且不调用 `conversation.send` 的契约测试。
